# Transferencia local de Nutrequine Pro

El responsable externo puede reconstruir el módulo a partir de `transferencia/NUTREQUINEPRO_FUENTE.zip`. El manifiesto de evidencia registra el SHA-256 del ZIP y el commit del que se obtuvo. Los binarios se generan por equipo destino a partir de `app/package-lock.json` y se colocan en un directorio nuevo. El módulo usa React/Vite, Fastify y dos almacenes SQLite mediante `node:sqlite`. Se validó en Windows con Node 24.18.0, npm 11.16.0 y Chrome. El proyecto requiere Node 24.18 o superior.

## Instalación de ensayo y módulo distribuido

1. Compare el SHA-256 del ZIP fuente con el manifiesto y extraiga en una carpeta nueva. Con acceso al registro de npm, ejecute `npm ci` dentro de `app/`. Mantenga el lockfile.
2. Ejecute `npm run verify` y, después del build nuevo, `npm run test:e2e`. Para preparar el navegador use `npx playwright install chromium` o indique `REGRESSION_BROWSER_CHANNEL=chrome` si Chrome ya está disponible. La aplicación compilada opera por loopback.
3. Genere el módulo con `npm run package:module -- --destination "D:\\Nutrequine Instalacion Nueva"`, sustituyendo el destino por una ruta absoluta nueva con padre existente y fuera del checkout. Guarde `MODULE-MANIFEST.json` junto a su carpeta `app` y compare el inventario y sus SHA-256 antes de usar el módulo.
4. Para un entorno sintético nuevo use `node app/scripts/sqlite-admin.mjs directory --directory <ruta-privada-nueva>`, luego `node app/scripts/sqlite-admin.mjs init --database <negocio-nuevo>`. Provisione el primer ADMIN con `node app/server/admin.mjs --database <negocio-nuevo> --auth-database <acceso-nuevo> --mode new`. Pase por stdin un JSON privado con ID, nombre, login y contraseña generados por el responsable. La contraseña requiere 15 caracteres como mínimo y hasta 1024 bytes UTF-8. La [instalación local](../INSTALACION_LOCAL.md) contiene el procedimiento detallado y el ejemplo seguro de PowerShell.
5. Cree la configuración JSON sin BOM en un directorio privado. Ejecute `node app/server/main.mjs --config <configuración-privada>` desde el módulo. Compruebe el mensaje `LISTENING` y abra `http://127.0.0.1:<puerto>/`. Compruebe login autorizado y que la consulta sin sesión se rechaza. Guarde la ruta del módulo y la versión en un inventario privado.
6. En el ensayo, registre una venta, una devolución, un cobro y un gasto marcados como sintéticos. Verifique movimientos, deuda y PDF de balance. Reinicie el proceso y compruebe las mismas operaciones.

| Ajuste               | Origen                                                             | Validación                                                             |
| -------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `database`           | Ruta absoluta privada de negocio existente                         | `sqlite-admin inspect` y `verify`, sin inicialización al arrancar      |
| `auth_database`      | Ruta absoluta privada del acceso correspondiente al negocio        | Vínculo a ruta canónica, integridad y credenciales preparadas          |
| `port`               | Puerto local libre elegido por el responsable                      | Abrir solo en `127.0.0.1` en pruebas                                   |
| `frontend_directory` | `app/public-client` del módulo compilado                           | Recursos y logotipo desde el paquete                                   |
| Políticas de micros  | Documentos técnicos aprobados conservados en configuración privada | Revisar vigencia, familias, dosis y sustituciones antes de utilizarlas |

## Actualización, respaldo y recuperación

1. Detenga el servidor y cualquier escritor. Seleccione las rutas de negocio y acceso de la instalación explícitamente. Use `sqlite-admin inspect --database <negocio>` y `verify --database <negocio>`. Registre la versión, revisión, checksums y situación inicial en el inventario privado.
2. Con el script `app/scripts/sqlite-admin.mjs` del módulo, ejecute `backup --database <negocio> --destination <respaldo-nuevo>` y `verify-backup --backup <respaldo-nuevo>`. Conserve el archivo y su manifiesto. Al detener el servidor, copie el almacén de acceso y configuración en el área privada, verifique hashes y decida con el responsable cómo preservar cualquier auxiliar de SQLite pendiente. Una copia física requiere cierre completo de los procesos. La CLI comercial reconoce el esquema de negocio.
3. Restaure el respaldo en ruta nueva con `restore --backup <respaldo-nuevo> --destination <negocio-copia>` y verifique la copia. En esa copia ejecute `migrate --database <negocio-copia> --apply` si hay versiones pendientes. Añada `--adopt` exclusivamente si la inspección confirma una copia histórica reconocida y existe autorización. La aplicación no migra por su cuenta al iniciar.
4. Compruebe `PRAGMA integrity_check` y `PRAGMA foreign_key_check` mediante `sqlite-admin verify`. Verifique identificadores y recuentos, revisión, cantidades de movimientos por presentación, saldos, pagos, conciliación y costos históricos. Confirme que correcciones y reintentos conservan el historial. Para una ruta comercial nueva, el almacén de acceso anterior no es compatible. Vincule un archivo nuevo a un ADMIN histórico activo con `--mode link --authorize-link` bajo autorización y restablezca accesos mediante el procedimiento ADMIN. La [guía de recuperación](../RESPALDO_RESTAURACION.md) documenta el vínculo y las copias semánticas.
5. Para actualizar solo código, construya el módulo en un directorio paralelo, mantenga `database` y `auth_database` y cambie `frontend_directory` al nuevo módulo. Para cambios de esquema acuerde el corte con el responsable tras ensayar la copia. Arranque y compare con el inventario privado. Use `init` y `new` exclusivamente para instalaciones nuevas.
6. Ante falta de espacio, error de copia, integridad fallida o discrepancias, detenga la conmutación y conserve original, versión y copia fallida. Use un destino nuevo tras corregir la condición y valide de nuevo. Si hay que volver a la versión anterior y la base ya avanzó, use el respaldo previo a la migración con un par de acceso compatible, previa conciliación de cualquier escritura posterior. Conserve la versión fallida para diagnóstico. Revise espacio para una copia completa, los auxiliares y el respaldo antes de comenzar.

## Operación de referencia

- **Ventas y Clientes.** Confirme cliente, sede, fecha de entrega, unidad, peso, precio y condición de pago. En operación ordinaria la entrega explícita mueve stock. Rectifique y devuelva desde el documento original para preservar vínculos. El reintento del mismo comando conserva su identificador. Las reservas comerciales parciales y la reposición automática quedan excluidas.
- **Inventario.** Diferencie sacos de 25 kg, BASE de consumo interno y frascos de 2,2 kg. Compruebe cantidad y peso en un ajuste con motivo. Un remanente en gramos sin unidades no es vendible.
- **Producción.** Prepare microinsumos contra orden y registre núcleos reales al confirmar. Use una jornada con líneas de producto y cierre cada lote completo con sacos reales; los gramos estimados que no forman saco se registran como merma. Consulte versiones históricas separadas de las fórmulas macronutrientes activas.
- **Compras y Gastos.** Una recepción puede tener varios renglones y un único gasto al contado. Registre el flete como gasto independiente. Dé entrada a las cantidades actuales en el corte y trate gastos históricos según su fecha para evitar doble cómputo. Conserve los consumos históricos.
- **Cobros, costos y Balance.** Las aplicaciones y reversos de cobros son movimientos registrados. El cobro real del molino parte del teórico y admite diferencias. El servicio cobra S/250 por tonelada encargada. La proyección variable y la valoración comercial no sustituyen conciliación y cierres contables definitivos. El balance resume operaciones y caja. Mantenga separados costos informativos y gastos efectivamente registrados.
- **Usuarios.** ADMIN gestiona permisos, OPERATOR ejecuta las operaciones habilitadas y VIEWER consulta. Las políticas técnicas de preparación y sustitución se gestionan fuera del paquete y requieren aprobación. Verifique el alcance de cada comando en la matriz.

## Paso posterior bajo responsabilidad externa

La entrega se limita a reconstrucción y verificación local. Cualquier instalación en infraestructura online requiere autorización humana posterior, un entorno de ensayo del responsable, respaldo comprobado, validación de permisos y políticas aprobadas, ensayo de corte y rollback, y una ventana planificada por su equipo. En NQP26-40 se trabajó por loopback con datos sintéticos, sin operaciones sobre servidores, DNS, dominios o datos empresariales.
